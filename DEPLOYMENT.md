# Deploying Raket

One Render web service, one MongoDB Atlas cluster, one Cloudinary account, and
an APK built against the service's real URL.

Everything below was run against this tree, except where it says it could not
be — and where that is the case it says what is missing rather than pretending.
Nothing here has been deployed: this container has no Render, Atlas, Cloudinary,
Google or Expo credentials, so the parts that need an account are written as
steps for you, in order, with nothing to guess.

## The architecture, and why

```
   phone (customer, rider, shop, kitchen)        browser (administrator)
        Expo app, token in the keystore               the admin SPA
                 │                                          │
                 │  Authorization: Bearer <jwt>             │  Cookie: accessToken
                 │  https://<service>/api/v1                │  (HTTP-only, same-origin)
                 └──────────────┬───────────────────────────┘
                                │
                    ONE Render web service
            Express API  +  the built admin SPA at /
                                │
                        MongoDB Atlas
                  (orders, catalogue, users)
                                │
                         Cloudinary
                       (uploaded images)
```

**Two apps, two front doors, one API, one database.** A customer order placed
on the phone is in the backoffice list immediately because there is only one
database behind both, and an administrator moving an order to "preparing" is
visible on the phone for the same reason. That is asserted end to end by
`api/src/scripts/checks/order-flow.check.mjs`.

**Why the admin SPA is served by the API** rather than from a static site on its
own domain: the backoffice authenticates with an HTTP-only cookie, which is the
one transport a cross-site scripting bug cannot read. Same-origin keeps that
cookie on `SameSite=Lax` — not the third-party `None` mode browsers are
restricting — and means no CORS, no credentialed preflight, and no reason to
move the admin JWT into `localStorage` where a script could take it. The admin
is still a separate application with its own login and its own pages; it is not
the customer app with extra buttons.

The cost is one real limitation, stated plainly: **when the service is asleep,
the browser has nothing to render.** The API serves the admin HTML, so the first
response has to arrive before any React loading screen can appear; until then
you see the browser's own slow-load or error page. The in-app waking screen
covers everything after that first paint — the service sleeping or redeploying
while a tab is open, and the database dropping — and says what it is waiting
for, with a retry. No amount of client code can put a branded screen in front of
an HTML document that has not been delivered. If you need one, read
[A separate admin origin](#a-separate-admin-origin), which costs more than it
sounds like.

## 1. MongoDB Atlas

1. **Create a project and a cluster.** <https://cloud.mongodb.com> → new project
   → **Build a cluster** → **M0** (free). Pick the region nearest Hindaun that
   Atlas offers — Mumbai (`ap-south-1`) — and keep it in the same part of the
   world as the Render region, or every query pays the round trip twice.
2. **Create a database user.** *Database Access* → *Add New Database User* →
   password authentication. Give it **Read and write to any database**, or
   narrow it to the one database if you prefer; it needs nothing else, and in
   particular it does not need `atlasAdmin`. Let Atlas generate the password and
   store it in your password manager. Do not reuse a password from anywhere.
3. **Allow Render to connect.** *Network Access* → *Add IP Address*.

   A Render free web service has **no static outbound IP**, so there is no
   address to allow, and the only rule that works on the free plan is
   `0.0.0.0/0` — the whole internet. That is a real tradeoff and worth being
   clear about: it means your cluster's endpoint is reachable from anywhere, and
   the only thing standing between a stranger and your data is the database
   user's password. So:
   - a long, random, unique password, generated by Atlas;
   - least privilege on that user, as above;
   - no other service sharing the credential;
   - and when this carries real orders, a paid Render instance with a static
     outbound IP, after which you can replace `0.0.0.0/0` with that one address.
4. **Copy the connection string.** *Database* → *Connect* → *Drivers*. It looks
   like:

   ```
   mongodb+srv://<user>:<password>@<cluster>.mongodb.net/?retryWrites=true&w=majority
   ```

   Add the database name before the `?`, or everything lands in `test`:

   ```
   mongodb+srv://<user>:<password>@<cluster>.mongodb.net/raket?retryWrites=true&w=majority
   ```

   URL-encode the password if it contains `@ : / ? # [ ] %`.

This string is a credential. It goes in Render's environment settings and
nowhere else — not in a commit, not in a `.env` file you push, not in a chat
message or a screenshot. The API never logs it: a boot that fails on bad
configuration prints variable *names* only, which
`deploy.check.mjs` asserts.

## 2. Cloudinary

The API has had Cloudinary integration all along
(`api/src/config/cloudinary.config.ts`); it needs keys, not code.

1. <https://cloudinary.com> → sign up → **Dashboard**.
2. Copy **Cloud name**, **API Key** and **API Secret**.
3. Enter all three in Render ([step 4](#4-environment-variables)).

**The API secret is server-side only.** It must never appear in a `VITE_*` or
`EXPO_PUBLIC_*` variable: both of those are compiled into bundles that ship to
browsers and phones, where anyone can read them. There is no client-side upload
path in this codebase — the browser posts the file to
`POST /api/v1/admin/uploads/image`, which is authenticated, and the server
talks to Cloudinary. Keep it that way.

With the three values set, `GET /api/v1/image-presets` starts reporting
`uploadsEnabled: true` and the backoffice shows its upload buttons. Without
them it hides those buttons and offers preset tiles instead, so nobody picks a
file and is then refused.

**What the upload endpoint enforces**, all of it asserted in
`deploy.check.mjs`:

| | |
|---|---|
| Signed in | 401 otherwise |
| Role | `admin`, `store_owner` or `restaurant_owner`; a customer gets 403 |
| Folder | one of `banners`, `categories`, `dishes`, `product-categories`, `products`, `restaurants`, `stores` — anything else is a 400 naming the real ones |
| Folder × role | a shop owner may upload `products` and `stores`, not `banners` or `categories`; admin may upload all of them |
| Type | PNG, JPEG, WebP or AVIF; anything else is a 400 that names the accepted types |
| Size | 5 MB; over that is a 400 that names the limit |
| Transport | `secure: true`, so every stored URL is `https://res.cloudinary.com/…` |
| Memory | `multer.memoryStorage()` — nothing is written to disk, so there is no temporary file to leak or clean up |

The Content-Security-Policy in `api/src/index.ts` already allows
`https://res.cloudinary.com` as an image source, so uploaded images render in
the backoffice rather than being blocked by Helmet.

## 3. The Render service

`render.yaml` is committed at the repository root, so the quickest path is a
blueprint:

> <https://dashboard.render.com> → **New** → **Blueprint** → pick this
> repository → Render reads `render.yaml`, creates **raket-api**, and prompts
> for each `sync: false` variable.

Setting it up by hand instead, these are the exact values:

| Field | Value |
|---|---|
| Type | **Web Service** |
| Runtime | **Node** |
| Region | **Singapore** (nearest free region to Hindaun) |
| Root directory | *(empty — the repository root)* |
| Build command | `bash ./render-build.sh` |
| Start command | `cd api && npm start` |
| Health check path | `/health` |
| Plan | Free to start; see [Cold starts](#cold-starts-on-the-free-plan) |

**Root directory must be the repository root, not `api/`.** The build needs
both apps, and the API resolves the admin bundle at `../../admin/dist` relative
to `api/dist`.

`render-build.sh` does, in order:

1. `npm ci --include=dev --prefix admin`
2. `npm run build --prefix admin` → `admin/dist`
3. asserts `admin/dist/index.html` exists
4. `npm ci --include=dev --prefix api`
5. `npm run build --prefix api` (typecheck, then tsup) → `api/dist/index.js`
6. asserts `api/dist/index.js` exists

**`--include=dev` is not decoration.** Render sets `NODE_ENV=production`, and
npm then skips `devDependencies` — which is where `vite`, `tsc` and `tsup`
live. Without the flag `npm ci` succeeds and the build fails two commands later
with `vite: not found`, which reads like a missing dependency rather than a
stripped one.

Both lockfiles are committed (`admin/package-lock.json` was missing and has been
generated), so `npm ci` is reproducible and a transitive release cannot change
what ships.

**`cd api && npm start`, not `npm start --prefix api`:** `npm start` runs `node
dist/index.js`, and that path is resolved against the working directory.

**Do not set `PORT`.** Render injects it and the API reads it.

### What the service answers

| Path | |
|---|---|
| `/health` | readiness, outside `/api/v1` and outside the rate limiter |
| `/api/v1/**` | the API. An unknown path here is a JSON 404, never the admin HTML |
| `/` and every other path | the admin SPA, with client-side routes like `/orders/<id>` falling back to the shell |

The shell is served `Cache-Control: no-cache` and Vite's fingerprinted assets
`max-age=31536000`, so a deploy is picked up immediately without re-downloading
the bundle every visit.

### The readiness policy, exactly

`GET /health` answers:

```json
{ "status": "ok", "ready": true, "database": "connected", "uptimeSeconds": 143 }
```

- **200** only when mongoose reports a live connection.
- **503** with `"ready": false` and the real state (`connecting`,
  `disconnected`, …) when it does not.

The API connects to MongoDB **before** it listens, so anything that answers at
all has connected once. What the 503 adds is the case afterwards: an Atlas
failover or a network blip drops the connection, mongoose reconnects in the
background, and every request in between fails. The old handler returned a flat
`{"status":"ok"}` and would have called that healthy. It no longer does, which
is what takes the instance out of rotation, and the log now carries
`Database connection lost` / `Database reconnected` so there is a reason to read
rather than a silence between "connected" at boot and a wall of timeouts.

`/health` is deliberately outside `/api/v1`: a platform health check and a
client's cold-start probe must never spend a customer's rate-limit budget.

## 4. Environment variables

Render dashboard → the service → **Environment**. Never in a commit.

### Required

| Variable | Notes |
|---|---|
| `NODE_ENV` | `production`. Without it the admin SPA is not served and cookies are not `secure`. |
| `MONGODB_URI` | From [step 1](#1-mongodb-atlas). |
| `JWT_SECRET` | 32+ characters of randomness. `render.yaml` has `generateValue: true`, so Render makes one and you never see or handle it. By hand: `openssl rand -base64 48`. |

In production the API **refuses to start** if a required variable is missing, if
`JWT_SECRET` is one of the published example values, or if it is shorter than 32
characters. One failed boot lists everything that is wrong, by name, with no
values — so a fresh service is not configured one redeploy at a time.

### Image uploads

| Variable | |
|---|---|
| `CLOUDINARY_CLOUD_NAME` | |
| `CLOUDINARY_API_KEY` | |
| `CLOUDINARY_API_SECRET` | **Server-side only.** |

Absent, the API still runs and uploads are reported as off.

### Optional, with defaults

| Variable | Default | |
|---|---|---|
| `PORT` | — | Injected by Render. Do not set it. |
| `LOG_LEVEL` | `info` | |
| `JWT_EXPIRES_IN` | `7d` | |
| `CORS_ORIGIN` | empty | **Leave empty in this topology.** The backoffice is same-origin; an empty allow-list is the safe default. |
| `PAYMENT_PROVIDER` | `razorpay` | Only matters once gateway keys exist. |
| `GOOGLE_CLIENT_IDS` | empty | Google sign-in off. |
| `RAZORPAY_KEY_ID` / `_KEY_SECRET` / `_WEBHOOK_SECRET` | empty | Online payment off; cash on delivery works. |
| `STRIPE_SECRET_KEY` / `_PUBLISHABLE_KEY` / `_WEBHOOK_SECRET` | empty | Only with `PAYMENT_PROVIDER=stripe`. |
| `FIREBASE_SERVICE_ACCOUNT` | empty | A **path** to a JSON file on the server, never the JSON itself. Push off. |
| `ADMIN_BOOTSTRAP_EMAIL` / `_PASSWORD` / `_NAME` | empty | Creates the first admin at boot when there is no shell. Set, deploy, sign in, **delete**. See [§5](#5-the-first-admin-account). |

`api/.env.example` is the full list with the reasoning for each.

## 5. The first admin account

Two routes. Pick the second if you have no shell — Render's **Shell** tab is a
paid-instance feature, so on the free plan it is the only route there is.

### Without a shell, from the dashboard

Render dashboard → the service → **Environment** → add three variables:

| Name | Value |
|---|---|
| `ADMIN_BOOTSTRAP_EMAIL` | the address you want to sign in with |
| `ADMIN_BOOTSTRAP_PASSWORD` | a long password of your own, 12 characters minimum |
| `ADMIN_BOOTSTRAP_NAME` | your name (optional) |

Save. The service redeploys, and on boot — after the database connects, before
it listens — the account is created. The log says
`Admin bootstrap created an admin`. Sign in at `/login`.

**Then delete those two variables and save again.** The log warns about it on
every boot while they are still there, because a password sitting in a
dashboard leaks with the dashboard. Deleting them does not remove the account.

What it refuses, rather than doing quietly: one variable without the other, a
password under 12 characters, and this repository's committed demo password. It
never prints the password, and a bad value is logged and skipped rather than
taking the API down with it. Setting a new password and redeploying is also how
you recover a forgotten one.

### With a shell

Render dashboard → the service → **Shell**, then:

```bash
cd api
NODE_ENV=production npm run seed:admin -- \
  --email you@yourdomain.com \
  --password '<a long unique password>'
```

Type the password into that shell. Do not put it in a file, a commit, or a
message. The script never prints it.

**In production this script refuses to run without both arguments**, and
refuses the demo email and the demo password this repository has committed
(`admin@chowly.app` / `chowly12345`). That used to be the silent fallback with
a warning printed afterwards — accurate and useless, because by then the
account existed, with a public password, on a deployment with a public URL. It
now fails before the database is even opened and names the command to run
instead.

One thing to know before you run it on a live database: **an existing account
with the same email is updated, password included.** That is deliberate — a
forgotten test login should be recoverable — but it means running it with a
real administrator's address resets their password. Use the address you intend
to keep.

Then sign in at `https://<your-service>.onrender.com/login`. The backoffice is
admin-only: any other role is sent to `/no-access`, and signing in with a
customer account on the login page discards the session rather than leaving a
customer's cookie on the backoffice origin.

Optional demo catalogue, if you want something on the shelves to look at:

```bash
cd api
npm run seed:categories     # the category strips
npm run seed:restaurants    # six example Hindaun kitchens
npm run seed:stores         # one example kirana with real stock
```

Skip the last two to start empty and enter real shops through the backoffice.
**Never run `npm run reset:demo` against a database with real orders** — it
drops the seeded catalogue, orders and baskets.

## 6. The mobile app

The app needs the service's real URL, which does not exist until the service
does. There is nothing to guess here, and a build pointed at the wrong host is
an APK that cannot reach anything.

```bash
cd mobile
# The deployed API, including /api/v1.
export EXPO_PUBLIC_API_URL="https://<your-service>.onrender.com/api/v1"
```

### Without a computer

`.github/workflows/android-build.yml` runs the build on GitHub's machines, so
the only thing you need is the Actions tab in a browser.

1. [expo.dev](https://expo.dev) → your account → **Access tokens** → create one
   and copy it.
2. This repository → **Settings** → **Secrets and variables** → **Actions** →
   **New repository secret** → name it `EXPO_TOKEN` and paste the token. The
   token belongs there and nowhere else.
3. **Actions** tab → **Build Android app** → **Run workflow**. Paste the API
   URL including `/api/v1`, leave the profile on `preview` for an installable
   APK, and run it.

It checks the URL is `https://` and ends in `/api/v1` before spending any build
time, typechecks, then hands off to EAS. The download link appears on
expo.dev → your project → **Builds**, 15–30 minutes later.

### With a computer

Either EAS:

```bash
npx eas init          # fills app.json's blank extra.eas.projectId; needs an Expo account
npx eas build --platform android --profile preview     # APK
npx eas build --platform android --profile production  # app bundle
```

…or locally, per `BUILDING.md` § Building the APK (needs JDK 21 and the Android
SDK, and re-applies two `gradle.properties` edits after every `prebuild
--clean`).

Three guards worth knowing about:

- **`https` turns off cleartext HTTP in the build.** `app.config.ts` derives
  `usesCleartextTraffic` from the URL, so an `https://` API removes the
  permission from the manifest by itself. Never ship a build pointed at
  `http://` — on a release APK that permits unencrypted HTTP to any host, and a
  customer's address and order can be read on a café's wifi.
- **A distributable EAS build with no `EXPO_PUBLIC_API_URL` is refused.**
  Without it the app falls back to `http://localhost:8000/api/v1`, which on a
  phone is the phone; the APK would install, open, and never reach Raket. The
  `development` profile is exempt, because a dev client gets its JavaScript
  from a Metro server at run time.
- **A hand-built APK in that state says so.** The warm-up screen reports that
  the build has no API address rather than telling the customer to check their
  connection.

Update the API first when you ship both. Most fixes live in the API, so a new
APK against an old API still shows the old behaviour.

## 7. Optional integrations

Each is off by default, and both clients **ask the server** what is configured
rather than assuming — so nothing shows a control that cannot work.

### Google sign-in

1. Google Cloud Console → *APIs & Services* → *Credentials*.
2. Create a **Web** OAuth client. Its id is what goes in `GOOGLE_CLIENT_IDS`
   (API), `VITE_GOOGLE_CLIENT_ID` (admin) and
   `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` (mobile) — the same id in all three.
   Counter-intuitive but correct: Google writes the *web* client id into the
   `aud` of every ID token, including the one the Android app sends, and that is
   what the API verifies.
3. Also create an **Android** OAuth client with your signing key's SHA-1, or
   native sign-in fails with `DEVELOPER_ERROR` before a token exists. It never
   appears in an audience, so it does not go in `GOOGLE_CLIENT_IDS`.
4. The client **secret** is not needed anywhere. The clients obtain an ID token
   themselves and the server verifies the signature; no secret, no redirect
   dance.

A bug worth noting, because it only ever affected the browser: the Google
endpoint returned a signed-in user **without setting the auth cookie**. The
backoffice has no access to the token in the body — it reads the session from
an HTTP-only cookie — so Google sign-in returned 200 and the next `/auth/me`
came back 401, bouncing straight back to the login page. The phone was
unaffected, which is why it survived. The cookie is now set, exactly as a
password login does.

### Online payment (Razorpay or Stripe)

Server half: set `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` (or
`PAYMENT_PROVIDER=stripe` and the Stripe pair). `GET /api/v1/payment-methods`
then reports `online.available: true` and the app believes it.

App half: `react-native-razorpay` is not a dependency yet, so the sheet cannot
open on a device. `BUILDING.md` § Known gaps has the three commands and the one
flag. **Until both halves are done, cash on delivery is the only method that
works**, and the app says so rather than failing at the Pay button — UPI, card,
netbanking and wallet are greyed out with a reason.

Webhooks, once keys exist:

| Provider | URL | Secret |
|---|---|---|
| Razorpay | `https://<service>/api/v1/webhooks/razorpay` | `RAZORPAY_WEBHOOK_SECRET` |
| Stripe | `https://<service>/api/v1/webhooks/stripe` | `STRIPE_WEBHOOK_SECRET` |

Both are mounted with `express.raw` **before** any JSON parser, because each
gateway signs the exact bytes it sent. Do not move them.

### Push notifications

`FIREBASE_SERVICE_ACCOUNT` is a path to the service-account JSON on the server,
never the JSON itself: a multi-line private key in an environment variable ends
up in logs and process listings. Render's filesystem is ephemeral, so this
needs a secret file or a mounted disk — and `expo-notifications` is listed in
`mobile/package.json` but the client half is not wired up, so push is off at
both ends today.

## Cold starts on the free plan

A Render free web service **spins down after about 15 minutes with no traffic**.
The next request waits for a container to start, Node to boot, and MongoDB to
connect before anything is served — tens of seconds, not milliseconds. Free
services also have no uptime guarantee and a monthly instance-hour budget.

There is no trick that fixes this, and pinging your own service on a timer to
keep it awake is both against the spirit of the free plan and a waste of the
same instance-hours it is spending. The honest fixes are a paid instance, or
designing for the wait. Both clients do the latter:

**Mobile.** The native splash is hidden as soon as the **fonts** are ready — a
local task that finishes in milliseconds. It is never held on a network call,
because a held splash is an app that looks frozen, with no spinner, no
explanation and no way to retry.

Over the navigator sits a Raket-branded warm-up screen — same green, same mark
as the native splash, so the hand-off is invisible — which probes `/health` and
shows *"Starting Raket… Waking up our servers — this can take a little longer
after a quiet spell."* Probes back off `1s → 2s → 3s → 5s → 8s → 10s`, capped at
10s so a service that returns at 70 seconds is noticed at 70 and not at 120,
with an overall ceiling of **120 seconds**. After that it says it cannot reach
Raket and offers **Try again**.

While that runs, **every API request waits at a gate**
(`mobile/src/lib/api-gate.ts`). The home screen alone opens banners, categories,
product rails, stores and restaurants, with the session restore alongside them;
without the gate a sleeping service turns one slow wake-up into six or seven
simultaneous "Can't reach Raket" screens, several behind tabs nobody has opened
yet, each needing a manual retry — and per-query retries would hit the waking
service eighteen times while it boots.

Three properties of that gate matter:

- **It opens on failure too.** A customer whose network is genuinely down still
  reaches the app, its normal error states and its retry buttons. A gate that
  only opened on success would be the blank-screen trap it exists to prevent.
- **It is not a retry.** Nothing re-sends a request; a held request has not been
  sent yet. **No order and no payment can be submitted twice because of it** —
  and mutations are configured `retry: false` in both clients, so nothing else
  re-sends a non-idempotent POST either. Only `GET`s are retried, twice, and
  never on a 4xx.
- **Recovery refetches.** If requests failed before the API came back, reaching
  ready invalidates the query cache, so the customer is not left looking at an
  app full of stale errors.

**Admin.** The limitation at the top of this document applies: the API serves
the admin HTML, so nothing of ours can paint before the first response. What is
covered is everything after it. `/auth/me` failing on the transport — or with a
503 from a service whose database has not connected — used to be read as
"signed out", which sent an administrator to a login form where the right
password also failed. Those two cases are now told apart: a 401 means signed
out, a transport failure or a 503 shows the waking screen, which polls
`/health` on the same backoff, explains itself, offers **Check now** and **Try
again**, and refetches once the API answers.

**First request after a deploy or a sleep is slow. That is the plan, not a
bug.** When it stops being acceptable, the fix is a paid instance.

## Verifying a deployment

```bash
# Readiness, and whether the database is actually connected.
curl -i https://<service>/health

# The admin shell.
curl -I https://<service>/

# A client-side route must fall back to the shell, not 404.
curl -I https://<service>/orders

# An unknown API path must stay JSON.
curl -i https://<service>/api/v1/not-a-real-route

# The catalogue, which is public.
curl -s https://<service>/api/v1/stores | head -c 400
```

Then in a browser: sign in at `/login`, reload the page (the session must
survive, which proves the cookie), and sign out.

Locally, the suite covers all of this and more:

```bash
cd admin && npm ci && npm run build      # the API serves this
cd ../api && npm ci
npm install --no-save mongodb-memory-server   # once; downloads a MongoDB binary
npm run check
```

Fifteen suites. The three that matter most for a deployment:

- **`deploy.check.mjs`** boots the API the way Render does — `NODE_ENV=production`
  against a throwaway MongoDB — and asserts the production-only half of
  `src/index.ts`: the readiness policy, the admin shell and its cache headers, a
  client-side deep link falling back to the shell, an unknown `/api` path
  staying a JSON 404, the upload endpoint's authorisation and limits, a customer
  refused on every admin route, the cookie set on login and cleared on logout,
  and `SIGTERM` shutting down cleanly inside a platform grace period. It also
  asserts the four configurations the service must **refuse** to start with.
- **`order-flow.check.mjs`** places a cash-on-delivery order as a customer,
  finds the same order in the backoffice, moves it through two statuses as an
  administrator, reads the new status back as the customer, and checks that a
  customer can neither change a status nor add a product nor read somebody
  else's order. Then an administrator creates a product and a signed-out
  customer sees it.
- **`route-coverage.check.mjs`** compares the API's real route table against
  every path both clients call, which is the only thing standing between two
  codebases that agree by hand.

`/health` is not in either client's `lib/api.ts` — it is not under `/api/v1`, so
it lives in `lib/health.ts` in both, which is also why `route-coverage` does not
see it.

## A separate admin origin

Only if you have decided the pre-wake admin page is worth it. It is not a
configuration change, it is a different security model, and everything in this
section has to be done and verified in a real browser before it is safe:

- `CORS_ORIGIN` set to the admin's exact origin, and credentialed CORS verified
  — including the preflight on every non-GET.
- The auth cookie moved to `SameSite=None; Secure`, which is third-party, which
  browsers are actively restricting. Safari's ITP and Chrome's third-party
  cookie work both bear on whether this keeps working.
- `trust proxy` and TLS correct on both hosts so `Secure` cookies are actually
  set.
- Login, reload-restores-session, logout, and expiry tested in Chrome, Safari
  and Firefox, in normal and private windows.

What is **not** an acceptable workaround: moving the admin JWT into
`localStorage` so cross-origin login works. That trades a cookie no script can
read for a token any injected script can, on the one surface that can change
every order and every price in the system.

Until all of that is done and tested in a browser, the single-origin topology in
`render.yaml` is the safe one, and the admin waking screen covers every case
except the very first paint.
