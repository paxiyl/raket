# Chowly — v1 Planning Brief & Implementation Plan

_Created 2026-09-03. This file is the source of truth for Chowly v1; update it in place as decisions change._

**Related documents:** [mobile design](../design/mobile-design.md) — locked visual system, screen inventory, and board prompt for `mobile/`.

## Context

Chowly is a Deliveroo-style food delivery platform built as a three-app workspace at
`c:\Users\emmab\Desktop\mern-delivery-platform`. At the time of writing the repo is nearly empty of
product code:

- `api/` — TypeScript Express 5 scaffold (Helmet, rate limiting, Winston, error contract, graceful
  shutdown, `/api/v1` router). **No database, no auth yet.**
- `mobile/` — Expo SDK 57 + expo-router with typed routes; only a placeholder `src/app/index.tsx`.
- `admin/` — bare Vite 8 + React 19 + oxlint shell; only the starter `App.tsx`.

The goal of v1 is the first slice where the platform is genuinely real: a customer can sign up, save a
delivery address, browse restaurants, pay by card, and watch the order progress while a driver — using
the *same* mobile app under a different role — claims and delivers it, with an admin backoffice running
the catalogue and the fulfilment queue behind it.

## 1. Specification summary

### Product and users

| User | Surface | Core outcome |
|---|---|---|
| Customer | Mobile (Expo) | Order food from a nearby restaurant to a saved address and know where it is |
| Driver | Mobile (same app, role-routed) | Go online, claim a ready order, deliver it, advance status |
| Admin | Web (Vite React) | Run catalogue, drivers, and the live order queue; see payments |

**Success criteria for v1:** a card-paid order can travel end-to-end — customer checkout → Stripe
confirmation → admin sees it → driver claims it → customer sees `delivered` — with no manual database
edits at any step.

### V1 scope

**Mobile (customer):** splash → welcome (Continue with email; Continue with Google shows an alert stub)
→ signup → address capture (GPS + manual edit) → login → home (delivery address in header with a
dropdown to switch) → tabs **Home, Search, Orders, Profile** → restaurant → dish → basket → checkout →
order tracking. Favourites are a saved list inside Profile (heart icons still on cards); no Favourites tab.

**Mobile (driver):** role-routed shell — online/offline toggle, queue of `ready` unassigned orders,
atomic claim, then `picked_up` → `delivered`, plus a delivery history list.

**Admin:** login, dashboard metrics, categories CRUD, restaurants CRUD, dishes CRUD, driver management
(create/approve/deactivate), order queue (status override, manual driver assignment), payments list.

**API:** Mongo/Mongoose, Passport JWT (dual transport), catalogue, cart validation, orders, Stripe
PaymentIntents + verified webhook, Expo push dispatch, role/ownership authorisation.

### Explicitly out of scope for v1

Vendor/restaurant self-serve accounts · live courier GPS on a map · ratings and reviews · promo codes
and vouchers · scheduled orders · multi-restaurant baskets · in-app chat or calls · refunds and disputes
UI (Stripe dashboard only) · tips · order editing after payment · social login beyond the alert stub ·
i18n · `routes/v2`.

### Core journeys

1. **First run (customer):** splash → welcome → signup (name, email, password, phone) → permission
   prompt → GPS reverse-geocode prefills an editable address → saved as default → home.
2. **Order:** home lists categories + restaurants → restaurant → add dishes to basket (single restaurant
   per basket; switching prompts to clear) → basket → checkout (address, fee breakdown) →
   PaymentSheet → success → tracking screen.
3. **Fulfilment:** payment confirms the order → admin drives `preparing` → `ready` → driver queue →
   claim → `picked_up` → `delivered`. Customer's tracking polls while open; push fires on each transition.
4. **Failure states:** payment declined (order stays `pending_payment`, retryable) · webhook late (poll
   fallback on the success screen) · location permission denied (manual address form) · claim race
   (loser sees "already taken", list refreshes) · offline (cached last state + retry banner).

### Data model (Mongoose)

- **User** — `name, email (unique, lowercase), passwordHash, role: customer|driver|admin, phone,
  isActive, expoPushTokens[], favouriteRestaurants[ObjectId], driver: { isOnline, lastLocation }`.
- **Address** — `userId, label, line1, line2, city, postcode, instructions, location: GeoJSON Point,
  isDefault`.
- **Category** — `name, slug, imageUrl, sortOrder, isActive`.
- **Restaurant** — `name, slug, description, imageUrl, categories[], address, location: Point,
  deliveryFee, minOrder, prepTimeMinutes, rating, ratingCount, isOpen, isActive`. `rating` and
  `ratingCount` are admin-entered, not user reviews.
- **Banner** — `imageUrl, title, subtitle, target, startsAt, endsAt, isActive, sortOrder`; admin-managed
  promotional cards for the Home carousel.
- **Dish** — `restaurantId, name, description, imageUrl, price, categoryId, isAvailable`.
- **Order** — `orderNumber, customerId, restaurantId, items[{ dishId, name, unitPrice, quantity }],
  subtotal, deliveryFee, serviceFee, total, currency, status, paymentStatus, stripePaymentIntentId,
  deliveryAddress (snapshot, not a ref), driverId, timeline[{ status, at, by }]`.
- **ProcessedWebhookEvent** — `eventId (unique), type, processedAt` for Stripe idempotency.

**Money is stored as integer minor units** everywhere (no floats), and every total is recomputed
server-side from current dish prices at checkout — client-sent prices are never trusted.

**Order status machine:** `pending_payment → paid → confirmed → preparing → ready → picked_up →
delivered`, plus `cancelled`. Transitions are validated server-side against an allowed-transition map
and the acting role; the driver claim is a single atomic
`findOneAndUpdate({ status: "ready", driverId: null })`.

### Roles and permissions

Customer reads the catalogue and owns only their own addresses, orders, and favourites. Driver reads
the unassigned `ready` queue and mutates only orders where `driverId` equals their own id. Admin has
full access; admin accounts are seeded or admin-created — never self-signup. Every list query is scoped
by owner in the service layer, never by trusting a client-supplied id.

### Architecture

Three deployables against one API at `/api/v1`. Auth is one Passport JWT strategy using
`ExtractJwt.fromExtractors([cookieExtractor, ExtractJwt.fromAuthHeaderAsBearerToken()])` — admin gets
an HTTP-only cookie, mobile gets a Bearer token held in `expo-secure-store`. Business logic lives in
`services/`, controllers stay thin, and `route → controller → service → model` is the enforced flow.

**Integrations:** MongoDB Atlas · Stripe (PaymentIntents + PaymentSheet + webhook) · Cloudinary
(signed uploads from admin) · Expo Push · `expo-location` reverse geocoding.

### Non-functional

Helmet + rate limiting already in place; auth endpoints get a stricter limiter. `sanitizeFilter` on
Mongoose plus Zod validation on every request body/query. No secrets, tokens, cookies, or raw bodies in
logs. Indexes on `Order.customerId`, `Order.driverId`, `Order.status`, `Restaurant.location` (2dsphere),
`Dish.restaurantId`, `User.email`. Tracking polls at ~10s only while the screen is focused.

### Delivery and testing

MongoDB Atlas free tier; API + admin on Render or Railway; mobile via an **EAS development build**
(Expo Go cannot run Stripe RN or Android remote push). Done = the flow verified by actually running it,
with automated tests only where a silent bug is expensive: auth/permissions, order total computation,
status-transition rules, and Stripe webhook idempotency.

## 2. Confirmed decisions

1. One mobile app serving customer **and** driver, routed by role after login.
2. Customer scope as listed; four tabs (Home, Search, Orders, Profile), Favourites inside Profile.
3. Admin manages dashboard, drivers, restaurants, dishes, categories, payments.
4. Roles in v1: customer, driver, admin. No vendor role.
5. JWT via HTTP-only cookie for admin **and** Bearer + SecureStore for mobile, one strategy.
6. Address capture: `expo-location` GPS → reverse geocode → user-editable → coordinates stored.
7. "Continue with Google" is an alert stub only.
8. Driver claims from a queue; admin can also assign manually.
9. Status freshness: polling while the screen is open + Expo push on transitions. No sockets.
10. Stripe PaymentSheet in-app, PaymentIntent from the API, verified webhook confirms.
11. Images via Cloudinary signed uploads.
12. Total = subtotal + flat per-restaurant delivery fee + percentage service fee.
13. Atlas + Render/Railway + EAS dev build.
14. Manual verification, with tests on money and auth.
15. The mobile visual system is locked in [the design document](../design/mobile-design.md) — teal
    palette, Inter, 12px inputs / 16px cards / 28px sheets, white ink on the Home teal header.
    Implementation encodes those exact values as semantic tokens; it does not invent new ones.
16. Ratings and Home banners are admin-managed data (Restaurant `rating`/`ratingCount` + Banner
    collection), not a review system or an offer engine.

## 3. Assumptions (defaults chosen during discovery; still open to change)

- **A1** Basket lives on the device (Zustand + persisted storage); server revalidates and recomputes at checkout.
- **A2** Signup creates customers only; drivers are created/approved in admin and log into the same mobile app.
- **A3** Order auto-advances to `confirmed` on successful payment; admin drives `preparing`/`ready`.
- **A4** Admin UI = Tailwind v4 + shadcn/ui (skill installed) + React Router + TanStack Query.
- **A5** Mobile data = TanStack Query + Zustand for auth/basket; Uniwind theme via the `expo-uniwind-theme` skill.
- **A6** Search = server-side name match across restaurants and dishes; no filters/sorting in v1.
- **A7** Driver queue is "all `ready` unassigned orders" — no radius filter until real volume exists.
- **A8** Access token ~7 days, no refresh-token rotation in v1; logout clears cookie/SecureStore.
- **A9** Seed script creates admin, categories, a few restaurants + dishes, and one driver.
- **A10** `mobile/src/app` gets route groups `(auth)`, `(customer)`, `(driver)` under the existing typed-routes setup.

## 4. Open risks and unknowns

- **R1 — RESOLVED (2026-09-05): currency is USD.** Orders are created and charged in `usd`, and the app
  formats minor units as `$`. Stripe does not operate in every market (notably Nigeria), so the
  platform's Stripe account country still has to support USD payouts.
- **R2 — CONFIRMED (2026-09-05): Expo Go can no longer run the app.** Adding `@stripe/stripe-react-native`
  made a dev build mandatory; `mobile/android/` is now generated and the app id is `com.chowly.app`.
  iOS dev builds still need a Mac or EAS cloud builds.
- **R3 — Cloudinary signed uploads** put a secret in the API only; admin must never hold the API secret.
- **R7 — Map keys are build-time.** The tracking map uses `react-native-maps`; `ANDROID_MAPS_KEY` and
  `IOS_MAPS_KEY` live in `mobile/.env` and are injected by `mobile/app.config.js` into the native
  project, so rotating either one needs a dev-client rebuild, not just a Metro restart. Restrict the
  Android key to `com.chowly.app`. The route drawn between pickup, courier and drop-off is a straight
  polyline — no routing service is wired up, so it is not a driven path.
- **R4 — Push tokens on shared devices** must be removed on logout or the next user gets the previous
  user's notifications.
- **R5 — Money rounding** on the percentage service fee: fix the rounding rule once, in one helper.
- **R6 — Free-tier cold starts** on Render/Railway will make the first request after idle slow; the
  mobile client needs sane timeouts and retry.
- **R7 — TypeScript 7 / ts-node incompatibility** already bit the API scaffold (now on `tsx`); expect
  similar friction from tooling that calls the TS compiler API.

# Implementation plan

Milestones are independently verifiable. Each ends with a working, runnable slice.

### M0 — Foundations: database, auth, theming, shells

**API** (`nodejs-scaffolding` skill, MongoDB + auth modes):

- `npm i mongoose passport passport-jwt jsonwebtoken` (+ types); `src/config/database.config.ts` with
  `mongoose.set("sanitizeFilter", true)` before connect, called from the startup path in
  [../../api/src/index.ts](../../api/src/index.ts) before listen, and disconnected inside the existing
  `shutdown()`.
- `MONGO_URI`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `ADMIN_EMAIL`/`ADMIN_PASSWORD` added to
  [../../api/src/config/env.config.ts](../../api/src/config/env.config.ts) and `.env.example`.
- `src/config/passport.config.ts` — one JWT strategy, `session: false`,
  `fromExtractors([cookieExtractor, fromAuthHeaderAsBearerToken()])`.
- `src/middlewares/auth.middleware.ts` — `requireAuth` + `requireRole(...roles)`.
- `src/models/user.model.ts`, `address.model.ts`; `src/services/auth.service.ts`, `user.service.ts`,
  `address.service.ts`; `src/controllers/…`; `src/routes/v1/auth.route.ts`, `address.route.ts`
  mounted in [../../api/src/routes/v1/index.ts](../../api/src/routes/v1/index.ts).
- Reuse the existing `hashValue`/`compareValue` in
  [../../api/src/utils/bcrypt.ts](../../api/src/utils/bcrypt.ts), the exception classes in
  [../../api/src/utils/app-error.ts](../../api/src/utils/app-error.ts), and `asyncHandler` — do not
  write new equivalents.
- `src/utils/cookie.ts` (`setJwtAuthCookie`/`clearJwtAuthCookie`), Zod schemas in `src/validators/`,
  stricter `authLimiter` alongside `apiLimiter` in
  [../../api/src/middlewares/rateLimiter.middleware.ts](../../api/src/middlewares/rateLimiter.middleware.ts).
- `src/scripts/seed.ts` + `npm run seed`.

Endpoints: `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`,
`GET|POST|PATCH|DELETE /addresses`, `PATCH /addresses/:id/default`.

**Mobile:** run the `expo-uniwind-theme` skill (Uniwind + Tailwind v4, semantic tokens, navigation
theme bridge, fonts, splash coordination, Sonner Native). Then `npx expo install expo-location
expo-secure-store`; add `src/lib/api-client.ts` (Bearer from SecureStore, 401 handling),
`src/store/auth-store.ts`, `src/features/auth/*`, and route groups `(auth)` [splash, welcome, signup,
login, address-capture] / `(customer)` / `(driver)` with a role-based redirect in
[../../mobile/src/app/_layout.tsx](../../mobile/src/app/_layout.tsx).

**Admin:** Tailwind v4 + shadcn/ui init, React Router, TanStack Query with `credentials: "include"`,
login page, protected `AppLayout` shell with sidebar.

**Verify:** register + login from mobile, cookie login in admin, `GET /auth/me` on both transports,
address saved with coordinates, seeded admin can sign in.

### M1 — Catalogue

API: `category`, `restaurant`, `dish`, `banner` models/services/controllers/routes; public reads
(including `GET /banners/active`), admin writes; `rating`/`ratingCount` editable on the restaurant form;
`POST /uploads/signature` for Cloudinary signed uploads. Admin: CRUD tables + forms + image upload,
including banner scheduling.
Mobile: home (address header + dropdown, category strip, restaurant list), search, restaurant detail,
dish detail, favourite toggle in Profile.

**Verify:** create a category/restaurant/dish with a real uploaded image in admin, see it in mobile,
search finds it, favourite persists across restart.

### M2 — Basket, checkout, Stripe

`npm i stripe` (API) / `npx expo install @stripe/stripe-react-native` (mobile, dev build required).
Order model + `src/services/order.service.ts` computing totals server-side from live dish prices;
`POST /orders` → order + PaymentIntent; **webhook mounted with `express.raw` before the global
`express.json` in [../../api/src/index.ts](../../api/src/index.ts)** and verified with the signing
secret; `ProcessedWebhookEvent` guards replay. Mobile basket, checkout, PaymentSheet, success + orders
list.

**Verify:** `stripe listen --forward-to localhost:8000/api/v1/payments/webhook`, pay with `4242…`,
order flips to `paid`/`confirmed`; replaying the same event changes nothing; a declined card leaves the
order retryable.

### M3 — Fulfilment: admin ops, driver mode, tracking, push

API: status-transition service with role rules, atomic driver claim, driver queue and driver-order
endpoints, admin assign/override, `expo-server-sdk` push dispatch on transitions, push-token
register/unregister. Mobile: driver shell (online toggle, queue, claim, active delivery, history),
customer tracking screen with focus-aware ~10s polling, `expo-notifications` registration.
Admin: order queue with live-ish refresh, status controls, manual assignment, driver management,
dashboard metrics, payments list.

**Verify:** two devices/simulators — customer pays, admin marks ready, driver claims (second driver is
rejected), advances to delivered; customer sees each change by poll and by push with the app closed.

### M4 — Hardening and deploy

Tests (Vitest + Supertest + `mongodb-memory-server`) for auth/permissions, total computation, transition
rules, webhook idempotency. Then Atlas, API + admin on Render/Railway, EAS dev-build profile, CORS
origins, `trust proxy` set from the real topology, and a README per app.

**Verify:** `npm test` green, deployed `/health` OK, admin against the deployed API, a dev build on a
physical device completing a real order.

## Verification (end to end)

1. `cd api && npm run seed && npm run dev` → `curl localhost:8000/health`.
2. `cd admin && npm run dev` → log in as the seeded admin, create catalogue with images.
3. `cd mobile && npx expo start --dev-client` → signup, address, browse, pay with a Stripe test card.
4. Admin advances the order; a second device logged in as the seeded driver claims and delivers it.
5. Confirm the customer sees `delivered`, and `npm test` in `api` passes.
